# pyre.db

`pyre.db` describes tables and queries as python classes, writes the SQL statements that create,
fill, change and read them, and talks to a database through a server. The statements are written
by a mill that speaks either standard SQL (SQL:2016) or the dialect of one back end, and the
values a server reads back are turned into the types of their columns.

## Tables

A table is a class that derives from `pyre.db.table`, with one column per field:

```python
import pyre.db

class Reading(pyre.db.table, id="readings"):
    """
    One value a day, by city
    """

    # the city
    city = pyre.db.str(maxlen=32).notNull()
    # the day
    day = pyre.db.date()
    # the value
    value = pyre.db.float()
```

The `id` is the name of the table in the database. The docstring becomes a comment block in the
statement that creates the table, and so does the `doc` of each field, at the end of its line. On
postgres, both are also recorded in the catalog of the server, with `COMMENT ON TABLE` and
`COMMENT ON COLUMN`, where `psql`'s `\d+` shows them; sqlite keeps the statement as it was written,
comments and all.

The names of tables, columns, indexes, constraints and databases are written as they are when they
are made of lower case letters, digits and underscores, start with a letter or an underscore, and
are not words the dialect reserves. Every other name is quoted, so a table may have a column named
`order` or `date`, and a name keeps its capitals: a table declared with `id="Readings"` is
`"Readings"` in the database, and postgres does not fold it to `readings`. Each dialect knows its
own reserved words: standard SQL those of SQL:2016, postgres those its `pg_get_keywords()` marks
reserved, sqlite all of its keywords. The mill's `identifier(name)` shows how a name is written.

### Column types

| type | holds |
|---|---|
| `pyre.db.bool()` | truth values |
| `pyre.db.int(bits=None)` | integers; `bits` of 16, 32 or 64 declares `SMALLINT`, `INTEGER` or `BIGINT`, and none `INTEGER` |
| `pyre.db.float(bits=None)` | floating point numbers; `bits` of 32 or 64 declares `REAL` or `DOUBLE PRECISION`, and none `DOUBLE PRECISION` |
| `pyre.db.decimal(precision, scale)` | fixed point numbers |
| `pyre.db.str(maxlen=None)` | text; unbounded unless `maxlen` is given |
| `pyre.db.bytes()` | strings of octets |
| `pyre.db.date()`, `pyre.db.time()`, `pyre.db.timestamp()` | dates, times of day, moments; `time` and `timestamp` take `timezone=True` to keep their offsets |
| `pyre.db.uuid()` | universally unique identifiers |
| `pyre.db.array(schema=...)` | arrays of another column type; `rank` gives their number of levels |
| `pyre.db.json()` | json documents: whatever `json.dumps` writes and `json.loads` reads |
| `pyre.db.reference(key=...)` | a foreign key, holding the values of the column it refers to |

### Decorations

Each decoration returns the column, so they chain:

- `primary()`: the column is the primary key;
- `unique()`: its values are unique across the rows;
- `notNull()`: it refuses `NULL`;
- `setDefault(value)`: its default; a column has a default only when it is given one, so a value
  left out of a row is `NULL`. `setDefault(pyre.db.null)` declares `DEFAULT NULL`;
- `references(key=...)`: it refers to the column `key` of another table;
- for references, `onDelete(action)` and `onUpdate(action)`, with the actions
  `pyre.db.noAction`, `restrict`, `cascade`, `setNull` and `setDefault`;
- for json columns, `verbatim()` keeps the text of the documents as written (postgres `JSON`
  rather than `JSONB`), and `asText()` reads them back as their text (see *Reading values*);
- for integers, `autogenerated()` lets the server assign the values (`GENERATED ALWAYS AS
  IDENTITY`), and `autogenerated(supplied=True)` lets a row bring its own instead (`GENERATED BY
  DEFAULT AS IDENTITY`). A row without a value for such a column leaves it to the server.

### Keys, checks and indexes of the whole table

```python
# the primary key, one field per call, in the order of the calls
Visit.pyre_primaryKey(Visit.year)
Visit.pyre_primaryKey(Visit.month)
# a unique constraint over the fields of one call; each call is a constraint of its own
Person.pyre_unique(Person.name, Person.phone)
# a foreign key
Reading.pyre_foreignKey(field=Reading.city, foreign=City.id)
# a check
Reading.pyre_check(Reading.low <= Reading.high)
# a check with a name, which an error reports when the check fails
Reading.pyre_check(Reading.low <= Reading.high, name="ordered")
# an index over the fields of one call, in order; each call is an index of its own
Granule.pyre_index(Granule.start, Granule.stop)
# a unique index
Granule.pyre_index(Granule.name, unique=True)
# an index over the rows that pass a predicate, with a name of its own
Granule.pyre_index(Granule.track, where=pyre.db.isNotNull(Granule.track), name="tracks")
```

A table derived from another includes its columns, keys, foreign keys, checks and indexes.

Unique constraints, foreign keys and checks take a `name`, which the statement declares with
`CONSTRAINT name`. A constraint without one is named by the server; postgres reports the name of a
violated constraint in the `constraint` of the exception it raises.

An index without a name of its own is named after its table and its fields:
`granules_start_stop_index`. `createTable` creates the indexes of the table right after it;
with `indexes=False` it leaves them out, so that a bulk load can fill the table first and build
them afterwards with `createIndexes(table)`. `createIndex(table, name)` and
`dropIndex(table, name)` create and drop one of them by its name.

## Queries

A query is a class that derives from `pyre.db.query`, with the tables it reads as keywords, and
one field per column of the selection:

```python
class Spread(pyre.db.query, weather=Weather):
    """
    How far apart the low and the high are
    """

    # a column of a table
    city = weather.city
    # a value computed from the columns
    spread = weather.high - weather.low
    # a conversion
    label = pyre.db.cast(weather.high, pyre.db.str())
    # the rows to keep
    where = weather.city != "Chicago"
    # how to group them
    group = weather.city
    # and in what order
    order = pyre.db.descending(weather.high)
    # and each distinct row once
    distinct = True
```

- A derived field is computed by the database, and its column is read back as it is.
- `pyre.db.cast(field, type)` converts a field to a column type; it can be selected and compared.
- `pyre.db.isNull(field)` and `pyre.db.isNotNull(field)` test for `NULL`.
- `pyre.db.like(field, pattern)` matches a pattern, in which a backslash escapes the wildcards
  `%` and `_`; the statement names the backslash as the escape character.
- `== None` compares with the literal `NULL`, which no row matches; use `isNull` instead.
- `pyre.db.isIn(field, values)` tests whether a field holds one of a list of values, written
  `field IN (…)`; an empty list is `FALSE`, since SQL has no empty list to write. In place of the
  list, a query of one column supplies the values from its rows, written `field IN (SELECT …)`.
- `pyre.db.negation(predicate)` negates any predicate, written `NOT (…)`. As SQL has it, a list
  that holds a `NULL` makes `negation(isIn(…))` true for no row.

A query joins one of its tables to the others with a `joins` clause, one join or a sequence of
them, in order:

```python
class Kinds(pyre.db.query, granule=Granule, product=Product):
    # the name of each granule
    name = granule.name
    # and the kind of its product
    kind = product.kind
    # every granule, with its product when it has one
    joins = pyre.db.leftJoin(product, on=granule.product == product.id)
```

`pyre.db.join(table, on=predicate)` keeps the rows that have a match, and
`pyre.db.leftJoin(table, on=predicate)` also keeps those of the other tables that have none, with
`NULL` in the columns of the joined table. The tables that are not joined come first; in a query
with joins they are crossed with `CROSS JOIN`, so that the joins read from left to right.

## Servers

| server | talks to |
|---|---|
| `pyre.db.postgres(name=...)` | a postgres server, through libpq 17 or later |
| `pyre.db.sqlite(name=..., database=path)` | a sqlite database, `:memory:` unless given a path |
| `pyre.db.backup(name=..., stream=...)` | a stream, to which it writes the statements |
| `pyre.db.folder(name=..., path=...)` | a folder, with a file of rows for each table |

Each server has `attach()`, which hands back the server, and `detach()`, and builds and executes
statements through `createTable`, `dropTable`, `insert(*rows)`, `update(*(template, condition))`,
`delete(table, condition)` and `select(query, limit=None, offset=None)`; `execute(*lines)` runs
statements given as text. `select` pages through the rows: `offset` skips that many of the first,
and `limit` keeps at most that many of the rest; both must be integers, or, in a prepared
statement, slots.

`select` hands back a generator, which reads the rows as it makes their records. postgres
declares a cursor over the selection, `DECLARE pyre_cursor_<n> NO SCROLL CURSOR WITH HOLD`, and
fetches `batch` rows at a time; sqlite reads each selection through a cursor of its own, `batch`
rows at a time. `batch` is a trait of the server, 1000 by default. Other statements may run on the
server while a selection is read, in a transaction or outside one, and a selection abandoned before
its last row closes its cursor. A cursor declared in a transaction that rolls back goes with it. A
selection abandoned while its transaction has failed leaves its cursor to the rollback, which takes
it when it was declared in that transaction; otherwise the next selection closes it. On
postgres, a prepared selection receives its whole result when it runs.

postgres and sqlite receive the values of `select`, `insert`, `update` and `delete` beside the
statement, as parameters, rather than inside it as literals, so nothing a value holds can change
what the statement does. A value of a column takes a bare placeholder, `$1` on postgres and `?1`
on sqlite, which the column gives a type; on postgres, a value that belongs to no column, such as
the right side of a comparison or the pattern of `like`, is cast to the type its literal would
have, `CAST($1 AS DATE)`, since nothing else says what it is. The mill's `parameters()` makes the
place that keeps them, the statement methods take it as `parameters=`, and its `drain()` hands
them over; `insertStatements` builds the statements of an insert one at a time, so each can run
with its own values. Statements built without it, the ones `pyre.db.backup` records among them,
hold their values as literals. On postgres, a session reads backslashes in text as ordinary
characters whatever the server was set up to do, which the literals rely on.

`insert`, `update` and `delete` take `returning`, and then hand back the rows they add, change or
remove: `returning=Granule` gives records of the table, as `select` does, and a field or a
sequence of fields, such as `returning=Granule.id`, gives records of those fields, read as
`row.id`. That is how a key the server assigns comes back. postgres and sqlite write `RETURNING`;
standard SQL has no such clause, so its mill refuses it.

`insert` also says what happens when a record meets a row with the same key: by default the
insert fails, as SQL has it; `existing="keep"` leaves the row that is there alone, and
`existing="replace"` writes the columns the record sets over it. The key is the primary key of
the table, or the fields of another unique constraint or index named by `key=`. postgres and
sqlite write `INSERT … ON CONFLICT … DO NOTHING` or `DO UPDATE`; standard SQL writes `MERGE`.
A selection of a whole table names its columns.

`load(*records)` inserts many records at once, all or nothing, and hands back the server. The
records are grouped by their table and by the columns they give values for, in the order the
groups first appear. postgres copies each group into its table with `COPY … FROM STDIN`, sqlite
runs one `INSERT` per group with `executemany`, and the other servers write the inserts that
`insert` writes. A load takes neither `returning` nor `existing`, so a record whose key is there
already raises `IntegrityError`, and the whole load is undone.

`insert` and `load` refuse a value for a column whose values the server assigns and takes from no
row, one declared `autogenerated()` without `supplied=True`, with `InterfaceError` naming the
column, unless they are given `generated="keep"`. Then standard SQL and postgres write
`OVERRIDING SYSTEM VALUE`, sqlite takes the value as it takes any id a row brings, and the copies
of postgres take it without being told.

`reproduce(source=…, tables=…)` makes the tables in the database of the server with the rows, the
keys and the indexes they have in the database of `source`, all in one transaction. A table comes
before the ones among them that refer to it, as `Table.pyre_referencedTables()` names them, and
tables that refer to each other in a cycle, and the ones that refer to them, are refused with
`NotSupportedError`, which names a few of them. Each table is made without its indexes and its
references to itself, filled `batch` rows at a time by `load(…, generated="keep")`, given its
indexes and, with `ALTER TABLE … ADD FOREIGN KEY …`, its references to itself, so that a row may
refer to one that comes after it; sqlite, which cannot add them, declares them with the table and
does not check them. Then each of its generated columns is told to go on after its largest value,
with `ALTER TABLE … ALTER COLUMN … RESTART WITH …`, which sqlite has no need of. With
`pyre.db.backup(stream=…, sql=<mill>)` as the server, the reproduction is a file of statements in
the dialect of the mill, which `psql -1 -f` or `sqlite3` runs as it is.

`pyre.db.folder(name=…, path=…)` keeps the tables of a database as files of rows in a folder,
which it makes when it attaches: `<table>.tsv` for each table, a line for each row, its values in
the order the table declares its columns, in the text format of postgres's copies. Values are
separated by tabs, a null is `\N`, a backslash escapes itself and the characters that would break
a line or a row, a truth value is `t` or `f`, octets are `\\x` and their hexadecimal digits, dates
and times take the form of the standard, and an array is written as postgres writes one,
`{{1,2},{3,NULL}}`, with an entry in double quotes when it would be misread without them. postgres
reads such a file with `COPY … FROM` or psql's `\copy`, and the folder reads every escape postgres
writes. A folder makes and removes tables, loads rows and reads whole tables back in the order they
were loaded. Its tables are read whole, so the requests about indexes and identities do nothing; a
record that leaves a value to the server is refused, and so is every statement, with
`NotSupportedError`. A transaction block that raises leaves the
files as it found them, and a folder removes tables only outside a block. Reproducing a database
into a folder and the folder into another database moves the database between back ends, in a form
neither of them owns.

The postgres bindings move rows in bulk. `connection.copyIn(statement)` starts a
`COPY … FROM STDIN` and hands back a context manager, whose `row(*values)` sends one row with its
values rendered as `execute` renders its arguments; the block keeps the rows when it ends and throws
them away when it raises. `connection.copyOut(statement)` starts a `COPY … TO STDOUT` and hands
back an iterator over the lines of text the server sends. A copy holds its session until it ends, so
the other threads that share the session wait for it. A copy out abandoned before its last line asks
the server to stop sending, outside a transaction; inside one, where a statement the server stops
would fail the transaction, it reads the remaining lines and throws them away. A `COPY` that moves
rows between the server and the client, sent through `exec`, `execute` or `send`, is refused with
`InterfaceError`.

`connection.stream(statement, *arguments, batch=1000)` runs a selection, with its arguments rendered
as `execute` renders them, and hands back an iterator over its rows in batches, each one a result of
at most `batch` rows, which libpq delivers in chunks of that size. A failure of the server partway
is raised when the iteration reaches it, after the rows that came before it. A stream holds its
session as a copy does. One abandoned before its last batch ends as an abandoned copy out does. A
session in the middle of an answer, whether a copy, a stream, or a statement sent with `send` whose
results have not been collected, refuses the statements its own thread sends, through `exec`,
`execute`, `prepare`, `execPrepared`, `describe`, `release`, `send`, `sendParams`, `sendPrepare`,
`sendPrepared`, `copyIn`, `copyOut`, `stream` or `pipeline`, with `InterfaceError`, since libpq
would throw the answer away to make room for them.

A prepared statement is rendered once and runs many times. `pyre.db.parameter(name, schema=None)`
is a slot for a value given when the statement runs; it stands where a value stands, in a
restriction, in the template of an update, or as a bound of a selection. In a template, the column
it fills gives it a type; in a restriction, `schema` says what it holds, as in
`Granule.name == pyre.db.parameter(name="name", schema=pyre.db.str())`, and a slot without one is
a mistake in the code that declared it; a bound is a number of rows. A slot that appears twice
takes one placeholder, and a constant next to a slot keeps its value at every run.
`prepareSelect(query, limit, offset)`, `prepareUpdate(template, condition, returning)` and
`prepareDelete(table, condition, returning)` take the arguments of `select`, `update` and `delete`,
and hand back a statement whose `run(**values)` fills in its slots, each value converted to the
type of its slot, and hands back what the call it mirrors hands back: the rows of a selection, one
at a time, the rows an update or a deletion changes, with `returning`, and nothing otherwise. A
slot without a value, or a value without a slot, raises `InterfaceError` before anything reaches
the database, and so does a statement with slots that runs without being prepared. postgres
teaches the session the statement on its first run, under a name of the form `pyre_prepared_<n>`,
and again on the first run after the server attaches to a new session; `close()`, or the end of a
`with` block, makes the session forget it. sqlite keeps the text, and its module keeps the
statements it has compiled. `pyre.db.backup` writes the statement anew at every run, with the
values as literals.

`runMany(rows)` runs a prepared statement once for each of `rows`, the values of its slots for each
run, as `run` takes them, `batch` runs at a time, each batch all or nothing. Every run is bound
before anything reaches the database. Each batch runs in a block of its own, a savepoint inside a
block that is open already: postgres sends it through a pipeline, as one segment, and the other
servers run its statements one at a time. A run that fails raises the exception of its condition,
whose `values` are the values of the run; its batch is undone, the batches before it are kept, and
the ones after it are not run. A statement that hands back no rows hands back nothing, and the
others hand back the records of every run, in order.

The postgres bindings expose the prepared statements of a session directly:
`connection.prepare(name, statement)`, `connection.execPrepared(name, *arguments)`,
`connection.describe(name)`, whose result reports the types of the parameters in `parameterTypes`
and of the columns in `types`, and `connection.release(name)`. A release works even in a failed
transaction, and finds nothing wrong with a name that holds nothing.
`connection.sendPrepare(name, statement)` and `connection.sendPrepared(name, *arguments)` do the
same without waiting, and their answers are collected with `result`, as those of `send`.

`connection.pipeline()` starts a pipeline: a context manager whose `execute(statement, *arguments)`,
`prepare(name, statement)` and `execPrepared(name, *arguments)` send statements without waiting for
the answers to the ones before them, and whose `sync()` ends a segment. Iterating over it hands back
the result of each statement, in the order they were sent; a statement that failed answers with a
result whose `check()` raises the exception of its condition, and the statements after it in its
segment with results whose status is `pipelineAborted`. The statements of a segment run in a
transaction of their own, unless they are inside one already, so a failure undoes its segment, and
the next segment runs. The result of a statement may be read before its segment ends. A pipeline
sends without waiting for the socket, and reads the answers that arrive while it waits for the one
it was asked for; it holds its session as a copy does, and the session refuses the statements sent
around it. The end of the block syncs what was sent, reads the answers that are left, and leaves the
pipeline.

Creating and dropping make it so: after `createTable(table)` the table exists, and after
`dropTable(table)` it is gone. By default, finding it that way already is an error; with
`existOk=True` on a creation, finding it there already is fine, and with `missingOk=True` on a
removal, so is finding it gone already. `existOk` looks only at the name: a table that exists
with other columns is accepted as it is. Databases and indexes take the same flags. The dialects
write them as
`IF NOT EXISTS` and `IF EXISTS`; postgres has no such clause for `CREATE DATABASE`, so its server
keeps the promise itself. Standard SQL has neither clause, so its mill refuses both flags.

A `with` block is a transaction: it begins when the block starts, commits when the block ends,
and rolls back when the block raises. On postgres, a transaction the server abandoned because a
statement in it failed is answered with a rollback when it commits; the block then raises
`OperationalError`, so its work is never lost silently.

A block inside a block is a savepoint, named `pyre_1`, `pyre_2`, … in the order they are set:
when it ends, its work stays in the transaction around it, and when it raises, only its own
work is undone and the transaction carries on, on postgres even after a statement in it failed.
An `update` of several rows and an `insert` with `returning`, which run several statements, run
them in a block of their own, so they keep all of their work or none of it. The postgres
bindings' `Transaction` nests the same way.

On postgres, `with db.lock("catalog.update"):` holds an advisory lock from the start of the block to
its end, whatever the transactions inside it do, so that one process at a time does what the lock
guards. The name becomes a key every process computes the same way, the first eight bytes of its
BLAKE2b digest; an integer is a key already. By default the block waits for the lock;
`wait=False` gives up at once when another session holds it, and `timeout=` after that many
seconds, raising `pyre.db.exceptions.LockError`. The other servers have no such locks, and refuse
them.

A failure raises one of the exceptions in `pyre.db.exceptions`, classified as the DB API has it:
`IntegrityError` for a violated constraint, `ProgrammingError` for a statement the database
cannot make sense of or about an object it does not have, `DataError` for a value that does not
fit, and `OperationalError` for the circumstances of the database, such as a lock held by another
session. Each carries the statement in `command` and the explanation of the database in
`diagnostic`. postgres names the condition with its five character `sqlstate`, and reports the
schema, table, column and constraint at fault. A failure inside a function on the server also
carries where it happened, the function and the statement in it, in `context`; when the function
ran a statement of its own, that statement is in `internalQuery`, and the place in it where the
server gave up is in `internalPosition`. sqlite names the condition with its extended result
code, such as `SQLITE_CONSTRAINT_PRIMARYKEY`, in `code`, and reports nothing else; a statement
that python's `sqlite3` module refuses before sqlite sees it, such as one given too few values,
raises `ProgrammingError` with an empty `code`. A run of a prepared statement among many carries the
values of its slots in `values`. A statement sent through a server that is not attached raises
`InterfaceError`.

A postgres session may be shared by threads: its calls take turns.

## Clusters

`pyre.db.backends.postgres.cluster` manages a postgres cluster: the data directory of a server,
and the server that runs on it. It implements the protocol `pyre.db.cluster`, and is its default.
It makes the cluster with `initdb` and starts and stops its server with `pg_ctl`, which it runs as
programs of their own, so it needs neither libpq nor a connection to the server. Its settings are
traits:

| trait | what it is | unset or default |
|---|---|---|
| `programs` | the directory with `initdb` and `pg_ctl` | found on the `PATH` |
| `data` | the data directory of the cluster | required |
| `socket` | the directory of the unix socket of the server | the data directory |
| `port` | the port, which also names the socket, `.s.PGSQL.<port>` | 5432 |
| `user` | the superuser `initdb` makes | the user who runs it |
| `authentication` | how the server authenticates its clients | `trust` |
| `encoding` | the encoding of the databases | `UTF8` |
| `locale` | the locale of the databases | the one of the environment |
| `addresses` | the network addresses the server listens on | none: the socket only |
| `durable` | whether the server makes sure its writes reach the disk | yes |
| `log` | the log file of the server | `<data>.log`, beside the data directory |

`authentication` applies to the socket and to the network alike. With `durable` off, `initdb` runs
with `--no-sync` and the server with `fsync=off`.

`init()` makes the cluster, unless the data directory holds one already; a data directory holds a
cluster when it has a `PG_VERSION`. `start()` starts the server and waits until it accepts
connections; it makes the socket directory, private to the user, if it is not there. `stop()`
stops the server, ending the sessions that are open, and waits until it is gone. `status()` says
whether the server runs. `remove()` stops the server and deletes the data directory, and, when the
socket has a directory of its own, the socket and lock a server leaves there, and then the
directory, unless something else lives in it. `restart()` removes the cluster, makes a new one, and
starts its server. Each one but `status()` hands back the cluster, and each one but `restart()`
leaves alone what is done already.

Failures go to the error channel `pyre.db.cluster`: a missing data directory setting, a server
program that is not where the cluster looks, and a program that fails, along with what it said.
`remove()` refuses to delete a data directory that holds no cluster, and leaves a cluster alone
when its server does not stop. The log survives `remove()`.

`bin/pyre-postgres` carries out one of these on the command line, and its exit status says
whether the server is left in the state the action promises: running after `start` and
`restart`, stopped after `stop` and `remove`, a cluster after `init`. `status` reports on the
server, and succeeds when it runs.

```
pyre-postgres restart --cluster.data=$HOME/db/catalog --cluster.user=catalog
pyre-postgres status --cluster.data=$HOME/db/catalog
```

An application that needs a cluster declares a facility of the protocol, `pyre.db.cluster()`, and
configures it like any other component.

### The clusters of the test suites

The suites `pyre-postgres.lib.tests`, `pyre-postgres.ext.tests` and `pyre-postgres.pkg.tests`
each run on a cluster of their own:

| setting | value |
|---|---|
| server programs | `postgres.bin` |
| data directory | `<staging>/pyre-postgres/<suite>/cluster`, under the staging area of the build |
| log | `<staging>/pyre-postgres/<suite>/cluster.log` |
| socket directory | `/tmp/pyre-<checksum>`, eight hex digits of a checksum of the data directory |
| port | 5432, which names the socket only; the server listens on no network address |
| superuser | `pyre`, trusted on the socket |
| encoding and locale | `UTF8` and `C` |
| durability | off |

The socket gets a short directory of its own, since a path to a socket holds about a hundred
characters, which a staging area can exceed. The checksum keeps the clusters of different suites
and builds apart.

The drivers find the server through libpq's environment: `PGHOST` names the socket directory,
`PGPORT` is 5432 and `PGUSER` is `pyre`, and `PGDATABASE`, `PGPASSWORD`, `PGSERVICE` and
`PGHOSTADDR` are removed, so that nothing left in the shell sends a driver to another server.
Before the first driver, once the prerequisites of the suite are built, the suite runs
`pyre-postgres restart`, which replaces whatever an earlier run left behind with a fresh cluster.
After the last driver, it runs `pyre-postgres remove`. A run of some of the drivers, or one that
fails, leaves the cluster up until the next run of the suite or a clean, `mm tests.clean` or
`mm <suite>.clean`, which removes it along with its log.

The fixture is configured by two make variables, given on the command line of `mm` or in the
user's mm configuration:

- `postgres.bin` is the directory with `initdb` and `pg_ctl`. The `--pkgdb` backends set it when
  they find a postgres server installed; otherwise it is the directory where the `PATH` finds
  `initdb`. The suites run when both programs are there, and skip their drivers when not.
- `postgres.fixture`, `yes` unless set, says whether the suites make clusters of their own. With
  `postgres.fixture=no`, they use the server that libpq's environment names, and run when `psql`
  can log in to its database `postgres`; when it cannot, the suites skip their drivers, with a
  warning that names the server, the port and the user that failed.

The drivers of the cluster itself are in `tests/pyre.pkg/db`, named `cluster_*`; the ones that
start a server run where the programs are, and are told `postgres.bin` on their command line.

## Dialects

Each server writes its statements with a mill, its `sql` facility. Postgres and sqlite default
to their own dialects; `pyre.db.server` and `pyre.db.backup` default to standard SQL, which is
also `pyre.db.sql`. The mills are `pyre.db.backends.standard.mill`,
`pyre.db.backends.postgres.mill` and `pyre.db.backends.sqlite.mill`. A server configured with
another mill writes in it, and the back end refuses what it does not understand.

| | standard SQL | postgres | sqlite |
|---|---|---|---|
| unbounded text | `CLOB` | `TEXT` | `TEXT` |
| strings of octets | `BLOB`, `X'00FF'` | `BYTEA`, `'\x00ff'` | `BLOB`, `X'00FF'` |
| dates and times | `DATE '…'`, `TIME '…'`, `TIMESTAMP '…'` | the same, with `WITH TIME ZONE` for values that carry an offset | quoted text |
| identifiers | refused | `UUID` | refused |
| arrays | `INTEGER ARRAY`, `INTEGER ARRAY ARRAY`; `ARRAY[1, 2]` | `INTEGER ARRAY` at every rank; `'{}'` when empty | refused |
| json documents | refused | `JSONB`, or `JSON` | refused |
| infinities, not a number | refused | `'Infinity'`, `'-Infinity'`, `'NaN'` | refused |
| databases | refused | `CREATE DATABASE`, `DROP DATABASE` | refused: a database is its file |
| a transaction | `START TRANSACTION` | the same | `BEGIN TRANSACTION` |
| indexes | refused: the language has none | `CREATE INDEX`, `DROP INDEX` | the same |
| `autogenerated()` | `GENERATED … AS IDENTITY` | the same | the id of the row: `INTEGER`, only for the whole primary key |
| paging | `OFFSET n ROWS FETCH FIRST m ROWS ONLY` | the same | `LIMIT m OFFSET n`, `LIMIT -1` for no limit |
| `returning` | refused | `RETURNING` | `RETURNING`, since sqlite 3.35 |
| `existing` | `MERGE` | `ON CONFLICT` | `ON CONFLICT`, since sqlite 3.24 |
| documentation | comments in the statement | the same, and `COMMENT ON TABLE`, `COMMENT ON COLUMN` | comments in the statement, which sqlite keeps |
| `existOk`, `missingOk` | refused | `IF NOT EXISTS`, `IF EXISTS`; the server keeps the promise for `CREATE DATABASE` | `IF NOT EXISTS`, `IF EXISTS` |
| a column left to its default | `DEFAULT` | the same | left out of the insert |

pyre.db supports sqlite 3.35 and later, the first with `RETURNING`; `ON CONFLICT` came in 3.24.
The dialect of sqlite knows the version of the library python is linked against, and on an older
one it refuses only the features that library lacks, when they are used: "sqlite 3.31.1 has no
syntax that returns the rows a statement changes; it needs 3.35".

A refusal raises `pyre.db.exceptions.NotSupportedError`, with an explanation that names what is
refused: "the column things.tag holds identifiers, which sqlite has no type for".

Postgres stores an infinite fixed point number only in a column without a precision, and
`pyre.db.decimal` always has one, so infinities fit only in floating point columns.

## Arithmetic

The operators of python become the functions of SQL, which do not always agree with python:

| python | SQL | difference |
|---|---|---|
| `a ** b` | `POWER(a, b)` | |
| `abs(a)` | `ABS(a)` | |
| `a % b` | `MOD(a, b)` | the remainder takes the sign of the dividend: `MOD(-7, 2)` is `-1`, while python's `-7 % 2` is `1` |
| `a // b` | `FLOOR((a) / (b))` | the division of two integers truncates toward zero before the floor, so `FLOOR(-7 / 2)` is `-3`, while python's `-7 // 2` is `-4` |

Where the difference matters, do the arithmetic in python.

## Reading values

A server turns each value it reads into the type of its column, and the row takes it as it is:

- postgres sends typed values; its arrays become tuples;
- sqlite keeps truth values as integers, fixed point numbers as floating point ones, and dates,
  times and moments as text; they come back as `bool`, `Decimal`, `date`, `time` and `datetime`;
- text is text, whatever it says: the text `"None"` is not `NULL`;
- a json document comes back parsed, as a dictionary, a list, a number, a truth value or `None`.
  A document whose top level is a string would read as text, so it is refused with
  `pyre.db.exceptions.DataError`, which names the column; a column declared with `asText()` is
  read as the json text of its documents instead, and holds any document.

When a postgres statement takes arguments (`run(statement, *arguments)` on a postgres server,
with placeholders `$1`, `$2`, …), lists and tuples become arrays, dictionaries json documents,
and `bytes`, `bytearray` and `memoryview` strings of octets; text with a zero byte is refused
with `DataError`, since postgres text cannot hold one.
